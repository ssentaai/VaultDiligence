# D1 — Initial Allocability Screen

## Inputs

Vault name:
Contract address:
Chain:
Archetype (dimensions; VT-N historical):
Caller type (human / agent):

## Source Rule

Every field: [value] | Source: [exact URL] | Date: [YYYY-MM-DD]
No URL = G2. No date = E(P). Never estimate.

## Process

Step 0 (RECOMMENDED — plan mode): Before invoking this command in execution mode,
        run a plan-mode session (shift+tab to enter) to argue out:
          a. Which counterparties are likely to be the bottleneck for this vault
             (operator, custodian, oracle, sub-strategy protocol, redemption queue).
          b. Which fields are at highest risk of returning G2 or G3 — typically the
             ones that depend on operator documentation rather than on-chain reads.
          c. Which findings-live triggers should be seeded BEFORE A1/A2 spin up.
             A trigger raised in plan mode survives into the execution session via
             findings-live.md. This is how the human's prior knowledge of the vault
             flows into the agent run without polluting the agent's reasoning chain.
          d. Whether build-field-map.py output (refresh first if stale) suggests
             any fields missing from knowledge/data-model/fields/ that this vault
             type would need.
          e. Run `python3 scripts/load-incidents.py --vault-type <VT>` to see
             prior failure patterns affecting this vault type. Each matched
             incident's diligence-signature fields are candidates to seed as
             findings-live triggers before A1/A2 spin up. See
             spec/incidents-schema.md.
        After this plan-mode session, switch to auto-accept mode and re-invoke
        this command. The plan IS the spec; the agents execute against it.

        This step is operationally optional but materially improves run quality.
        Boris Cherny's tip 6: "A good plan is really important to avoid issues
        down the line." For VaultDiligence, the cost of a bad plan is wasted agent
        steps and worse cross-pack lessons; for vault diligence, it can also be
        evidence that survived A6 review when it shouldn't have.

Step 1: Load the core rules. Load vault type definition.
        caller_type=agent: run four hard gates before anything else.
        Structure in {leveraged,looped} (composed/leveraged): confirm two documents required.

Step 2 (caller_type=agent only): Four hard gates. Any fail = a structured output with critical_conditions_present=true.

  GATE A — Instant Withdrawal
    Call vault.maxWithdraw(agent_address) on chain.
    Pass: full position returnable in one block. Fail: any queue or cooldown.
    Source: Etherscan call + ABI

  GATE B — Upgrade Timelock
    Call TimelockController.getMinDelay().
    Pass: >= 172800 seconds (48hrs). Fail: < 48hrs or no timelock.
    Source: Etherscan

  GATE C — Governance Concentration
    Query governance token top-10 holder share.
    Pass: < 60% of circulating supply. Fail: >= 60%.
    Source: Etherscan token holders or Dune

  GATE D — Agent Position Cap (always calculate, never a gate)
    Calculate: withdrawable_liquidity_usd * 0.02
    Source: DefiLlama + Etherscan

Step 3: Exit Liquidity Box. Three numbers. Three sources. Any unconfirmed = HARD GATE.

Step 4: T1 API calls for core fields. Every field: URL + date.

  TVL:          DefiLlama api.llama.fi/protocol/{slug} — cross-ref Morpho API.
                Flag divergence >5% as I (Investigate).
  Net APY:      Vaults.fyi share-price basis only. Exclude emissions.
                Cross-ref DefiLlama yields.llama.fi/pools.
  Yield vs RFR: FRED api.stlouisfed.org DGS3MO. Calculate bps difference.
  Slippage:     1inch api.1inch.dev at $1M, $5M, $10M. Exact token + chain.
  Timelock:     Etherscan — TimelockController.getMinDelay(). On-chain call.
  Audits:       Solodit solodit.xyz — search protocol name. Note scope + date.
  Bug bounty:   Immunefi immunefi.com/bug-bounty/{protocol}/ — note max payout.
  GLEIF:        api.gleif.org — confirm legal entity if named in docs.
  OFAC:         sanctionslistservice.ofac.treas.gov — screen named entities.

Step 4a: Vault issuer page and protocol documentation via Scrapling.

  Target pages in priority order:
    1. Vault issuer or curator site
    2. Protocol Gitbook or official docs
    3. Fund prospectus or offering memorandum (Management=delegated-offchain-IM, or an off-chain listed-security exposure)

  Extract:
    Rehypothecation prohibition: exact clause or absence noted.
    Redemption terms: standard and stress as stated by issuer.
    Team identity: named individuals, roles, LinkedIn or equivalent.
    Legal structure: entity name, jurisdiction, regulator.
    Curator risk framework: link and date.
    Stated position limits or concentration caps.

  If page is JS-rendered and web_fetch returns no content: use Scrapling
  browser mode. If Scrapling fails: classify the field as G2 with
  "issuer page inaccessible via automated retrieval" as the reason.
  Do not skip. Do not substitute a secondary source silently.

Step 4b: Web search for recent activity in the last 90 days.

  Search 1: "{vault name} incident OR exploit OR hack OR pause 2025 OR 2026"
    If found: surface as triggered condition with source URL and date.

  Search 2: "{vault name} OR {curator name} governance proposal 2025 OR 2026"
    If found: note in structural checks with URL and date.

  Search 3: "{vault name} OR {protocol name} audit 2025 OR 2026"
    Cross-reference against Solodit results from Step 4.

  Search 4: "{curator name} OR {issuer name} team site:linkedin.com"
    For RF05 team verification check.

  If any search result conflicts with Step 4 API data:
    Flag as I (Investigate). State both sources. Do not resolve silently.

Step 5: Fast red flag checks: RF01, RF03, RF04, RF05, RF28.

Step 6: Render.
  caller_type=agent: structured JSON (schema below).
  Otherwise: D1 markdown (structure below).
